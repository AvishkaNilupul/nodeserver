# Retained companion status observations

Contract accepted 2026-11-25. This is a local diagnostic record only. It cannot start, stop, reconnect, authorize, open a browser, send chat, create clips or change coordination. Existing helper journals, completion outboxes and the sole host SQLite writer remain unchanged. No new HTTP route or response field is added.

The running host records completed, uncached account reads accepted by the account manager's current revision. Cached, shared in-flight and superseded reads do not produce observations. The existing five-second clip-status refresh reads account status even when automatic clips are off; no separate poller is added. A first observation establishes a baseline, changed state produces a transition, and an otherwise unchanged state produces a checkpoint after sixty seconds only when another real read completes. A missed read or stopped host cannot manufacture a healthy checkpoint. An unavailable helper is recorded as unavailable, with no browser or playback observation.

Records contain only a fixed profile ID (primary, test or third), host observation time, reported browser/video timestamps, booleans and enumerated status/error codes. Account names, channels, stream IDs/titles, chat text/authors, command data, raw reasons/errors, authorization/device codes, mail, phone numbers, cookies, tokens, private paths and session identifiers are excluded by construction. `chatTokenPresent` is token presence, not proof of a valid chat grant. Error codes describe the current reported condition; `observedAt` is when the host noticed it, never an invented original error time. Browser/video freshness is calculated from the reported timestamps, separately from successful helper reads. The log uses the account UI's 45-second diagnostic freshness window; this is not send or clip eligibility. Existing stricter action gates, including the 15-second clip playback gate, remain unchanged. Future/invalid timestamps are unverified. Baseline/transition comparison excludes advancing source timestamps, so normal five-second checks do not flood the log.

The host writes `private/status.jsonl` and up to three numbered rotations, each at most 1 MiB (4 MiB total). The containing private directory is owner-only (0700); log files are 0600. Writes are synchronous, small and bounded, with no unbounded queue. Rotation preserves complete records. A failed partial append is truncated back when possible; a later write repairs an incomplete final record before appending or rotating, preserving preceding complete observations. Files/directories must be ordinary owner-owned entries; symbolic links and multiply linked files are refused. I/O failures return without changing runtime state and emit at most one static warning per process, with no raw exception text. A later successful read can resume recording; no lost observations are invented. Service start and graceful stop are explicit lifecycle records; a missing stop is not proof of a crash or its time.

Account pages keep playback, browser freshness and chat connection separate. A currently disconnected chat's error takes precedence over an old participation reason, and an enabled session with disconnected chat is labelled disconnected rather than healthy. Status display does not clear the error or perform recovery.

Verification covers true-read/cache/revision boundaries, change/checkpoint behavior, invalid or stale source timestamps, strict privacy fixtures, bounded rotation/modes, I/O failure isolation, restart baselines and UI error precedence. Deployment remains a separate, reviewed targeted copy of source files. Rollback restores only source; preserve newer logs, histories, intent journals, outboxes and the coordination database.
